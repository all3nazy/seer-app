# استرجاع النسخ الاحتياطي لمنصة سِير

هذا الدليل لاسترجاع النسخ اللي تأخذها «سِير أدمن» ← **النسخ الاحتياطي**.

## وش فيه كل نسخة
- **مكان النسخة ومدة بقائها:** كل نسخة في مخزن Supabase الخاص `platform-backups` داخل مجلد بتاريخها، مثل `2026-11-24/`. تبقى المجلدات ٣٠ يوم، والأقدم ينحذف تلقائيًا.
- **الجداول:** ملف لكل جدول في `public` و`private` باسم `<schema>.<table>.json.gz`. الملف مصفوفة JSON مضغوطة بـ gzip فيها كل الصفوف.
- **الحسابات:** الملف `auth.users.json.gz` فيه المعرّف، والبريد، والجوال، والتواريخ، والبيانات الوصفية (metadata). **ما فيه كلمات المرور.**
- **الفهرس:** الملف `manifest.json` فيه:
  - عدد الصفوف وحجم كل ملف وبصمته `sha256`.
  - آخر ترحيل في الكود (`app_migration`).
  - نسخة قاعدة البيانات إن كانت مسجّلة (`db_version`).
- **غير مشمول:**
  - الملفات المرفوعة، مثل صور إيصالات التحويل في `subscription-receipts` وغيرها من مخازن الملفات. انسخها من لوحة Supabase ← Storage إذا احتجتها.
  - إعدادات Supabase وVercel نفسها، مثل المفاتيح والمتغيرات وإعدادات الدخول.
- **تنبيه:** جداول `private` فيها أسرار تشغيلية، مثل مفاتيح الإشعارات الفورية وأسرار بوابات الدفع. تعامل مع ملفات النسخة كأنها كلمة مرور: لا ترسلها لأحد ولا تخزنها في مكان عام.

## ١) تحميل النسخة
1. ادخل «سِير أدمن» ← النسخ الاحتياطي. الصفحة للمالك فقط، وتحتاج التحقق الثنائي.
2. من صف النسخة المطلوبة حمّل `manifest.json`، ثم كل ملف تحتاجه. كل رابط صالح لمدة دقيقتين، وكل تحميل ينسجل في سجل العمليات.
   - لتحميل كل الملفات دفعة وحدة: من لوحة Supabase ← Storage ← `platform-backups` ← مجلد التاريخ ← حدد الكل ← Download.
3. حط الملفات كلها في مجلد واحد على جهازك باسم التاريخ، مثل `./2026-11-24/`.

## ٢) التحقق وتحويلها إلى SQL
من جذر المستودع:

```bash
node scripts/restore-backup.mjs ./2026-11-24 ./restore-sql
```

- **التحقق:** السكربت يقارن بصمة `sha256` وعدد الصفوف لكل ملف مع `manifest.json`. إذا لقى خطأ واحد يوقف ويطلب منك ما تسترجع.
- **الناتج:** ملف `<schema>.<table>.sql` لكل جدول. الملف يُدخل الصفوف بـ `jsonb_populate_recordset`، فتتطابق الأعمدة بالاسم، ومعه `on conflict do nothing`.

## ٣أ) الاسترجاع إلى مشروع Supabase جديد (الأفضل عند فقدان كامل)
1. **أنشئ المشروع:** أنشئ مشروعًا جديدًا في Supabase بنفس المنطقة، وفعّل pg_cron وpg_net من Database ← Extensions.
2. **طبّق الترحيلات:** طبّق كل ملفات `supabase/migrations/` بالترتيب في محرر SQL (أو بـ `supabase db push`)، لين يكون آخر ترحيل هو `app_migration` المذكور في الفهرس.
3. **أنشئ الحسابات أولًا:** الجداول تشير لـ `auth.users`، فلازم تنشئ الحسابات قبل الجداول.
   - من `restore-sql/auth.users.json` أنشئ كل حساب **بنفس المعرّف (id)** عبر Admin API بمفتاح الخدمة:
     `supabase.auth.admin.createUser({ id, email, phone, email_confirm: true, user_metadata, app_metadata })`
   - كلمات المرور ما تنحفظ في النسخة، فكل مستخدم يعيّن كلمة مرور جديدة من «نسيت كلمة المرور».
   - المشرفون يعيدون تفعيل التحقق الثنائي.
4. **أدخل الجداول:**
   1. في محرر SQL شغّل `set session_replication_role = replica;`. هذا يوقف المفاتيح الأجنبية والـ triggers مؤقتًا، فما يهم ترتيب الجداول.
   2. شغّل ملفات `restore-sql/*.sql`، جداول `public` ثم `private`.
   3. في الأخير شغّل `set session_replication_role = origin;`.
5. **أعد ضبط العدّادات:** الأعمدة `identity` لازم تكمل بعد أكبر قيمة. لكل جدول فيه `id bigint generated always as identity` شغّل:
   ```sql
   select setval(pg_get_serial_sequence('private.platform_audit','id'), coalesce((select max(id) from private.platform_audit), 1));
   ```
   الجداول المعنية: `platform_audit`، و`telegram_outbox`، و`login_attempts`، و`login_locks`، و`ip_blocks`، و`backup_runs`، و`support_templates`، وما يشبهها.
6. **حدّث Vercel:** في المشروعين (المنصة وسِير أدمن) حدّث `NEXT_PUBLIC_SUPABASE_URL` و`NEXT_PUBLIC_SUPABASE_ANON_KEY` و`SUPABASE_SERVICE_ROLE_KEY`، ثم أعد النشر.
7. **أعد ربط الخدمات:**
   - Webhook تيليقرام: من «سِير أدمن» ← الدفع والتليقرام.
   - روابط بوابات الدفع، إن وُجدت.

## ٣ب) استرجاع جدول واحد أو صفوف ممسوحة (نفس المشروع)
1. خذ ملف الجدول فقط، مثل `restore-sql/public.children.sql`.
2. **راجع قبل التشغيل:**
   - الإدخال يتجاهل الصفوف الموجودة (`on conflict do nothing`)، فيرجع الممسوح فقط ولا يغيّر الموجود.
   - لمنشأة وحدة: عدّل الملف ليصفّي `where organization_id = '<id>'`، أو استخدم «تصدير بياناتها» من ملف المنشأة.
3. شغّله في محرر SQL. إذا رفض بسبب مفتاح أجنبي لأن صف الأب ممسوح، استرجع جدول الأب أولًا. مثال: `children` قبل `attendance`.

## تصدير منشأة وحدة (حق نقل البيانات)
من ملف المنشأة اضغط «تصدير بياناتها»:
- **الناتج:** ملف JSON فيه كل جداولها اللي فيها `organization_id`، وأعضاؤها (المعرّف والبريد والجوال).
- **التسجيل:** التصدير ينسجل في سجل المنشأة.
- **الاستخدام:** يُسلَّم لمالك المنشأة عند المغادرة، ويمكن استرجاعه بنفس طريقة ٣ب.

## وش يضيف Supabase Pro لاحقًا
- **نسخ يومية تلقائية من Supabase:** على مستوى قاعدة البيانات كاملة (physical)، تبقى ٧ أيام، وتسترجعها من اللوحة بضغطة.
  - تشمل كلمات المرور المشفّرة، فما تحتاج تعيد إنشاء الحسابات يدويًا.
- **PITR (إضافة مدفوعة على Pro):** استرجاع لأي ثانية خلال فترة الاحتفاظ.
  - مفيد إذا انمسح شي بالغلط الساعة ١١:٠٣ وتبي ترجع للساعة ١١:٠٢.
- **مع Pro تبقى هذي النسخ اليومية مفيدة:** ننصح تخليها شغالة، لأنها:
  - مستقلة عن مشروع Supabase.
  - قابلة للتحميل.
  - تُستخدم لتصدير بيانات كل منشأة.
  - ويمكن تقليل مدة الاحتفاظ فيها بعد الترقية.

## المراقبة
- **وقت التشغيل:** النسخة اليومية تشتغل من Vercel Cron في مشروع **المنصة** (`seersa.vercel.app`) يوميًا الساعة ٠٠:٣٠ UTC، أي ٣:٣٠ فجرًا بتوقيت الرياض.
- **المتغيرات المطلوبة في مشروع المنصة:** `CRON_SECRET` و`SUPABASE_SERVICE_ROLE_KEY`.
- **التنبيهات على تيليقرام:**
  - **إذا فشلت النسخة:** يوصلك تنبيه فورًا.
  - **إذا ما فيه نسخة ناجحة خلال ٢٦ ساعة:** يوصلك تنبيه من مهمة `seer-backup-watch` في pg_cron، مرة كل ١٢ ساعة كحد أقصى.
