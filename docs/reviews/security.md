# مراجعة الأمان والخصوصية وقاعدة البيانات

النطاق: Issue #1، فرع المراجعة المحلي. لم تُنفذ هذه الترحيلات على قاعدة الإنتاج.

## ما تم التحقق منه

- أُجريت اختبارات SQL على PostgreSQL المدمج PGlite باستخدام الترحيل الأساسي والترحيلين الجديدين، مع أدوار `anon` و`authenticated` و`service_role` وبديل محلي لـ`auth.uid()`.
- أُعيد ترحيل المطابقة مرتين لمحاكاة وجود القيود المركبة والدالة الخاصة مسبقًا؛ نجح دون إسقاط قيود عزل المنشآت.
- يمنع RLS القراءة المجهولة والقراءة دون هوية والوصول إلى أطفال منشأة أخرى. يتحقق فحص الدور من جدول العضويات، لا من بيانات المستخدم القابلة للتعديل.
- يستطيع الموظف قراءة العمليات الخاصة بمنشأته، ولا يستطيع كتابة السجلات أو قراءة الفواتير وسجل التدقيق.
- يستطيع المالك/المدير الكتابة داخل منشأته فقط. تمنع المفاتيح الأجنبية المركبة ربط طفل أو فرع أو ولي أمر من منشأة أخرى. يمنع trigger نقل سجل بين المنشآت حتى لمدير عضو في كليهما.
- يسمح تعديل المنشأة بالاسم والنوع فقط، ويسجل عملية تدقيق. سجل التدقيق يحتوي معرّفات ووقت العملية، دون أسماء الأطفال أو أرقام الهواتف أو نسخ قيم السجلات.
- تمنع الصلاحيات تزوير سجل التدقيق أو حذفه، وتسحب صلاحيات TRUNCATE/REFERENCES/TRIGGER الموروثة من إعدادات المشروع الافتراضية. TRUNCATE لا يخضع لـRLS، ولذلك اختُبر رفضه صراحة.
- تهيئة المنشأة متاحة لـ`service_role` فقط. تتطلب مستخدمًا موثق البريد وتنشئ المنشأة وعضوية المالك والتدقيق ذريًا. ليست API عامة لإنشاء المنشآت.

## النتائج والحدود

- `npm exec vitest run tests/database.test.ts`: **14/14 ناجحة**.
- `npm run typecheck`: **ناجح**.
- `npm test`: **84/84 ناجحة** وقت المراجعة.
- يستبدل harness مخطط Auth بوظيفة محلية ويتجاوز تثبيت امتداد pgcrypto فقط لأن `gen_random_uuid` مدمجة. هذا تحقق فعلي للقيود والسياسات ومحرك SQL، ولا يعادل اختبار Supabase Auth أو PostgREST أو نشر الترحيلات على نسخة مماثلة للإنتاج.
- وفق فحص الإنتاج الذي أجراه الوكيل الرئيسي، توجد فروق عن `0001_core.sql` ولا يوجد سجل ترحيلات مُسجل. يجب مراجعة المطابقة وتسجيل خط أساس بشكل منفصل؛ لا تُعد تطبيق `0001_core.sql` على الإنتاج.
- لم تُدعَ واجهات دعوة المستخدمين أو يُرسل بريد أو يُنشأ حساب مدير أثناء هذه المراجعة. يظل إثبات جلسة المدير واختبار العمليات من المتصفح بعد تهيئة الحساب وترحيل المخطط مطلوبًا قبل اعتماد الإصدار.
- الرجوع الآمن: تعطيل واجهات الكتابة وسحب سياسات وصلاحيات الكتابة عند الحاجة، ثم الرجوع لإصدار التطبيق السابق. لا تحذف جداول العمليات أو بياناتها أو سجل التدقيق.


متابعة الإنتاج: بعد توجيه المالك بالمتابعة، طُبّق الترحيلان المراجعان وأصبح سجل الترحيلات مطابقًا لملفات المستودع. اعتُمد الأساس الموجود دون إعادة تنفيذه. نجح فحص SQL حي داخل معاملة ROLLBACK لعزل المراجع ورفض الوصول/الكتابة غير المأذونة، ولم تظهر تنبيهات أمنية. هذه المتابعة لا تثبت جلسة مدير أو دورة عمليات كاملة من المتصفح، اللتين تبقيان معلقتين حتى إعداد الحساب.


التفعيل المعتمد: خضع الجدول الخاص ودالة المطالبة واختبارات البريد الموثق والرفض وإعادة الاستخدام للمراجعة. أصبح التنفيذ المميز داخل private والواجهة العامة SECURITY INVOKER. الملاحظة المعلوماتية الوحيدة الباقية تتعلق بغياب سياسة على جدول الدعوات الخاص، وهو منع افتراضي مقصود مع سحب كل grants لأدوار API. لا توجد تحذيرات أمنية من المستشار في هذا الفحص. لم تُنشأ حسابات عبر SQL ولم تُطلب كلمة مرور من المالك.
